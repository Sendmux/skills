Approval of revision 5 and schedule_version 2 covers that saved content and tomorrow's send time. It does not approve edited content or an immediate send.

1. **Check access and client support.** Use a send-capable `smx_mbx_` key, appropriately scoped `smx_agent_` token or Mailbox OAuth grant, never a root key. Select the authorised mailbox; if the credential covers multiple mailboxes, include `mailbox_id` in the REST/CLI query or MCP's declared argument. Verify the installed client exposes the draft operations: the skill's candidate-source names do not prove released-client support. A durable self-registered agent profile must wait for owner acceptance and sending approval, then route sending through `sendmux-send-email` and the Sending API.
2. **Read the same saved draft.** Use `GET /api/v1/mailbox/drafts/{draftId}` to check its status, content, current `revision` and `schedule_version`. Do not assume they remain 5 and 2. Cancellation needs `mailbox.read` and `email.send`, plus approval of the saved content and send time. Confirm these still match the human's approval; if they changed, reconcile approval with the human before cancelling. Their cancellation request supplies confirmation to cancel the approved schedule.
3. **Cancel before editing.** Use `PATCH /api/v1/mailbox/drafts/{draftId}/schedule` with the current `expected_revision`, current `expected_schedule_version` and `"scheduled_for": null`. If the read still returns 5 and 2, those are the values to submit. On `409`, re-read and reconcile before retrying. Cancellation cannot undo sending that has already begun; if it has begun, reconcile that draft's status before considering another send. Proceed with editing only after successful cancellation, then read the resulting revision and schedule version.
4. **Edit with draft-write permission.** Editing needs `mailbox.read` and `mailbox.drafts.write`. Before composing, read `mailbox_get_identity` and use the returned identity or a user-supplied, verified identity. Wait for `ready`, then `PATCH /api/v1/mailbox/drafts/{draftId}` with the last read `expected_revision` and changed fields. Omitted fields retain their values; replacing `attachments` requires the complete desired list. On `409`, read the newer draft and review a merge rather than overwriting someone else's changes. Retain the returned versions.
5. **Obtain fresh approval.** Present the exact edited saved recipients, subject, bodies and attachments, and obtain approval to send them immediately. Bind approval to the resulting saved revision. The previous approval of revision 5 and tomorrow's schedule does not carry over.
6. **Send the approved revision immediately.** After confirming `ready`, use `POST /api/v1/mailbox/drafts/{draftId}/send` with the newly approved `expected_revision` and the current `expected_schedule_version`, even though this send is immediate after cancellation. Sending requires `mailbox.read` and `email.send`; `mailbox.drafts.write` cannot substitute. The authorised sender, recipient rules, credential send scope and current sending policy still govern the send. A connected outgoing account supplies a possible route, not permission. Sender, recipient and credential permissions are checked again when sending begins; revocation can stop a pending send.
7. **Reconcile retries on this draft.** A stale revision returns `409`; on any version conflict, re-read and reconcile the current versions, and re-approve any changed content before retrying. If the send response is lost, read this same draft and reconcile `queued` or `uncertain` status; never create a new message to retry. The stable draft ID and approved revision identify the send, without a separate send idempotency key. A scheduled time is an earliest send time, not a delivery guarantee.
